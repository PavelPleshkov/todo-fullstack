# Работа с ИИ в разработке: методичка по репозиторию

**Версия:** 1.1 (адаптация курса *AI tooling setup for developers v1.3* под монорепозиторий **todo-fullstack** и практику в **Cursor**).

**Назначение:** пошагово повторить тот же цикл для **любой новой задачи** (issue, таск курса, внутренний тикет): карта проекта → MCP → уточнение задачи → план → валидация плана → реализация → тесты → автоматический обзор → ручной review → merge.

**Исходное состояние проекта (как в примере issue #9):**

- Monorepo: **Yarn workspaces + Turborepo** (`apps/frontend`, `apps/backend`, `apps/docs`, `packages/*`).
- Карта репозитория: **`docs/CODEBASE_MAP.md`** — единственный ориентир по структуре, точкам входа, командам.
- Правила Cursor: **`.cursor/rules/project-architecture.mdc`** — всегда указывает на `CODEBASE_MAP.md` и локальную БД.
- Навыки (skills): **`.cursor/skills/Cartograph/SKILL.md`**, **`.cursor/skills/Definition-of-Ready/SKILL.md`**.
- GitHub: при необходимости — **GitHub MCP** в настройках Cursor (конфиг обычно в `.cursor/mcp.json`, файл в **`.gitignore`**, секреты не коммитить).

---

## Принципы (из курса + практика)

1. **Только разрешённые инструменты:** не подключать новые MCP, SaaS и модели без явного согласования проекта/клиента/курса.
2. **Не ждать идеальной настройки:** минимальный рабочий цикл сначала, улучшения потом.
3. **Выбор модели под этап:** «тяжёлые» модели — планирование, неоднозначность, архитектура; более быстрые/дёшевые — реализация, мелкие правки, итерации.
4. **Лимиты и стоимость:** следить за контекстом сессии и лимитами API при длинных чатах.
5. **Человек в контуре:** реализация, review и merge — ответственность человека; агенты могут галлюцинировать.
6. **Команда и безопасность:** артефакты (DoR, планы, карта) — общие; PAT/токены не в репозитории, при утечке — отозвать и пересоздать.

### Обозначения в примерах промптов (шпаргалка)

В текстах ниже используются пометки — **дословно копируйте нужные строки в запрос**, если курс или команда требуют явного указания:

| Пометка | Смысл |
|---------|--------|
| **`[ОБЯЗАТЕЛЬНО: MCP]`** | Агент должен получить данные **только через подключённый GitHub MCP** (не выдумывать текст issue из памяти). В Cursor: включён сервер `project-0-todo-fullstack-github` (или ваш аналог). |
| **`[ОБЯЗАТЕЛЬНО: @файлы]`** | В запросе должны быть вложения `@путь` — агент обязан опираться на эти файлы. |
| **`[ОПЦИОНАЛЬНО]`** | Усиливает контекст; можно опустить, если уже ясно. |
| **`[Ask mode]`** / **`[Agent mode]`** / **`[Plan mode]`** | Рекомендуемый режим Cursor для шага. |

## Этап 1. Карта проекта (Project map)

**Цель:** один понятный документ, по которому агент и человек не «переизобретают» структуру репо при каждой задаче.

### 1.1. Уже есть в репозитории

| Артефакт | Путь | Назначение |
|----------|------|------------|
| Карта кодовой базы | `docs/CODEBASE_MAP.md` | Приложения, пакеты, GraphQL, БД, команды `yarn dev` / `lint` / `build`, соглашения. |
| Правило Cursor (always-on) | `.cursor/rules/project-architecture.mdc` | Напоминание читать/обновлять `CODEBASE_MAP.md`; ссылки на `docs/local-database.md`, `apps/backend/.env.example`. |
| Skill «картограф» | `.cursor/skills/Cartograph/SKILL.md` | Заполнение/обновление `CODEBASE_MAP.md` по запросу пользователя. |

**Строка для других клиентов (из курса):** в конфигурации ассистента должно быть явно: *«Подробная архитектура: `docs/CODEBASE_MAP.md`»* — в Cursor это уже сделано через `project-architecture.mdc`.

### 1.2. Как обновить карту

1. В Cursor вызвать навык **Cartograph** (или вручную отредактировать `docs/CODEBASE_MAP.md` после крупных изменений).
2. После **больших** структурных изменений — обновить `CODEBASE_MAP.md` **в том же PR**, где меняется архитектура (согласовано с правилом проекта).

**Ожидаемый результат:** актуальный `docs/CODEBASE_MAP.md`; агент в чате может получить `@docs/CODEBASE_MAP.md` вместо длинного пересказа репо.

### 1.3. Примеры запросов агенту

**Обновить карту после изменений в монорепо (Agent или чат со skills):**

```text
[Agent mode]
Следуй навыку @.cursor/skills/Cartograph/SKILL.md.
Обнови @docs/CODEBASE_MAP.md по текущему состоянию репозитория: apps/*, packages/*, корневые скрипты, порты, GraphQL, качество. Не выдумывай порты — только из README и конфигов в репо.
После правок кратко перечисли, что изменилось в карте.
```

**Только проверить, не устарела ли карта (Ask mode):**

```text
[Ask mode]
[ОБЯЗАТЕЛЬНО: @файлы] @docs/CODEBASE_MAP.md @README.md
Сравни: есть ли в карте все workspace из корневого package.json? Что бы ты добавил в CODEBASE_MAP без правок кода — только список рекомендаций.
```

## Этап 2. Подключение инструментов через MCP

**Цель:** получать контекст задач (issue, комментарии) из IDE без постоянного переключения в браузер.

### 2.1. Выбор сервера

Для **GitHub** в этом проекте используется одобрённый **GitHub MCP** (настройка в Cursor: **Tools & MCP**). Для других трекеров курс предлагает официальные серверы (Linear, Jira/Atlassian, Asana и т.д.) — подставьте свой, если задачи не в GitHub.

### 2.2. Минимальный набор возможностей (как в курсе)

| Возможность | GitHub MCP (пример) |
|-------------|---------------------|
| Найти / перечислить работу | `search_issues`, `list_issues` |
| Открыть один элемент | `issue_read` (`method: get`) |
| Обсуждение | `issue_read` (`method: get_comments`) |
| PR | `pull_request_read`, `list_pull_requests` |

### 2.3. Аутентификация

- Часто **OAuth** или **PAT** (Personal Access Token).
- **Не коммитить** секреты: `.cursor/mcp.json` с токеном должен быть в **`.gitignore`** (в этом репо так и сделано).
- При утечке токена в чат — **немедленно отозвать** в настройках GitHub и выпустить новый.

**Ожидаемый результат:** из Cursor можно вызвать MCP и прочитать issue/PR (номер, тело, комментарии).

### 2.4. Примеры запросов (контекст задачи через MCP)

**Снять актуальное описание issue перед DoR / планом (курс: обязательно не «из головы»):**

```text
[Agent mode]
[ОБЯЗАТЕЛЬНО: MCP] Получи через GitHub MCP для репозитория PavelPleshkov/todo-fullstack:
- issue_read method=get issue_number=<N>
- issue_read method=get_comments issue_number=<N>
Дальше кратко перескажи: цель issue, критерии из текста, есть ли комментарии, меняющие scope. Не придумывай текст issue — только то, что вернул MCP.
```

**Проверить PR перед merge (сводка без локального `gh`):**

```text
[Agent mode]
[ОБЯЗАТЕЛЬНО: MCP] pull_request_read для owner=PavelPleshkov repo=todo-fullstack pullNumber=<P>:
- method=get
- method=get_files (perPage=100)
- method=get_status, method=get_check_runs
Сделай краткий отчёт: состояние PR, mergeable, число файлов, есть ли CI checks, совпадает ли scope с issue #<N>.
```

**После merge — зафиксировать состояние issue:**

```text
[ОПЦИОНАЛЬНО] [Agent mode]
[ОБЯЗАТЕЛЬНО: MCP] issue_read get для issue #<N> — закрыт ли, обновилась ли ссылка на PR в комментариях.
```

## Этап 3. Уточнение задачи под агента (Definition of Ready)

**Цель:** одна **спецификация**, которую можно вставить в Plan/Agent как единый промпт: цель, scope, ограничения, файлы, критерии приёмки, ссылки.

### 3.1. Skill DoR

| Файл | Назначение |
|------|------------|
| `.cursor/skills/Definition-of-Ready/SKILL.md` | Процесс DoR: секции Objective, Scope, Non-scope, Constraints, файлы, AC, риски. |

### 3.2. Запуск DoR

- В Cursor: команда/режим **`/dor`** или явный запрос: «сделай DoR по issue #N».
- Передать: текст issue, ссылку, скриншот; при необходимости — **`@docs/CODEBASE_MAP.md`**.

### 3.3. Сохранение спецификации

**Рекомендуемый путь файла (шаблон):**

```text
docs/task-issue-<N>-dor.md
```

**Пример из практики:** `docs/task-issue-9-dor.md` — спецификация по GitHub issue #9: fixed-кнопка темы, текст «AI», отступы 10px, ссылки на issue и скриншот, блок про одобренный GitHub MCP.

**Содержание DoR-документа (чеклист секций):**

1. **Objective** — что должно получиться в конце.
2. **Scope** — какие пакеты/папки трогаем (например, только `apps/frontend`).
3. **Non-scope** — backend, другие приложения, новые MCP — явно «не делаем».
4. **Constraints** — стек (Next.js, MUI), запреты (`position: absolute` для кнопки и т.д.), правила курса/клиента.
5. **Relevant files** — таблица: путь → зачем (как в `task-issue-9-dor.md`).
6. **Acceptance criteria** — нумерованный список: автотесты, `yarn lint`, ручные шаги в браузере.
7. **Links** — issue, скриншоты, `CODEBASE_MAP.md`.
8. **Risks** — что может пойти не так.

### 3.4. Ask mode

Использовать **Ask mode**, когда нужно **без правок кода**: уточнить требования, прочитать незнакомый модуль, сравнить варианты, разобрать ошибку. После ясности — переход к Plan или Agent.

**Ожидаемый результат:** файл `docs/task-issue-<N>-dor.md` (или эквивалент), готовый как **единый промпт** для следующих шагов.

### 3.5. Примеры запросов агенту (DoR)

**Полный проход DoR с MCP и картой (рекомендуемый шаблон):**

```text
[Agent mode]
Выполни Definition of Ready по навыку @.cursor/skills/Definition-of-Ready/SKILL.md.

[ОБЯЗАТЕЛЬНО: MCP] Сначала получи текст GitHub issue #<N> и комментарии через issue_read (get + get_comments) для PavelPleshkov/todo-fullstack.

[ОБЯЗАТЕЛЬНО: @файлы] Опирайся на @docs/CODEBASE_MAP.md и релевантные пути из репо (grep/чтение файлов), чтобы таблица «Relevant files» была с реальными путями, а не абстракцией.

Результат: создай или обнови файл docs/task-issue-<N>-dor.md на русском или английском (как принято в команде) со всеми секциями из SKILL: Objective, Scope, Non-scope, Constraints (включая «только одобренный GitHub MCP»), Relevant files, Acceptance criteria, Links, Risks.
Не коммить сам — только содержимое файла в ответе или запись в workspace по моей команде.
```

**Уточнить один пункт DoR без переписывания всего файла (Ask mode):**

```text
[Ask mode]
[ОБЯЗАТЕЛЬНО: @файлы] @docs/task-issue-<N>-dor.md
В разделе Acceptance criteria: достаточно ли критериев для ручной проверки в браузере? Предложи 2–3 недостающих пункта, без правок файла.
```

**Сверить DoR с планом курса по инструментам:**

```text
[Ask mode]
[ОБЯЗАТЕЛЬНО: @файлы] @docs/task-issue-<N>-dor.md
Есть ли в Constraints явный запрет на новые MCP и указание одобренного GitHub MCP? Если нет — процитируй готовую формулировку для вставки.
```

## Этап 4. Планирование с агентом (Plan)

**Цель:** безопасный **read-only** план: что менять, в каких файлах, как проверять.

### 4.1. Режим и модель

- **Cursor:** **Plan Mode** (аналог `/plan` + спецификация из DoR).
- Модель: **побольше / поновее** для планирования (курс рекомендует не экономить на качестве плана).

### 4.2. Входные данные для плана

Прикрепить в чат:

- `@docs/task-issue-<N>-dor.md`
- при необходимости `@docs/CODEBASE_MAP.md` и конкретные файлы из таблицы DoR.

### 4.3. Сохранение плана

**Рекомендуемый путь:**

```text
docs/plan-issue-<N>.md
```

**Пример:** `docs/plan-issue-9.md` — чеклист, текущее состояние файлов, шаги реализации, риски, раздел **Validation**, границы **Boundaries**, порядок коммитов.

**После первой реализации:** при расхождении плана с кодом добавить в конец плана секцию **As-built revisions** и ссылку на неё **в начале** файла (как в `plan-issue-9.md`), чтобы ревьюер не следовал устаревшим шагам.

**Ожидаемый результат:** утверждённый план в `docs/plan-issue-<N>.md`; кнопка **Build** в Cursor — старт реализации по плану.

### 4.4. Примеры запросов агенту (Plan mode)

**Старт плана с привязкой к DoR и карте:**

```text
[Plan mode]
/plan

[ОБЯЗАТЕЛЬНО: @файлы] Используй как единственную спецификацию задачи: @docs/task-issue-<N>-dor.md
Дополнительный контекст: @docs/CODEBASE_MAP.md

Составь план реализации и валидации: чеклист, затрагиваемые файлы с путями, риски, команды тестов/lint из acceptance criteria. Не выходи за рамки Scope/Non-scope из DoR. Выход: структура для сохранения в docs/plan-issue-<N>.md.
```

**Сузить план, если агент раздул scope:**

```text
[Plan mode]
Пересмотри план: убери всё, что не в `apps/frontend` (или укажи свой Scope из DoR). Без новых зависимостей без необходимости. Сохрани раздел Validation с ручными шагами из DoR.
```

## Этап 5. Валидация плана и старт реализации

### 5.1. Просмотр плана

- Прочитать **не меньше ~80%** плана: соответствие DoR, нет лишнего scope.

### 5.2. Проверки

- Не переусложнено ли (лишние абстракции, новые зависимости без нужды).
- Нет ли ветки «на будущее», не требуемой задачей.

### 5.3. Реализация

- **Cursor:** после согласования плана — **Build** или **Agent mode** с промптом вроде:  
  *Implement strictly per `docs/plan-issue-<N>.md` and `docs/task-issue-<N>-dor.md`.*
- Модель: можно **быстрее/дешевле**, чем на этапе плана (курс).

**Ожидаемый результат:** изменения в коде в границах scope; затронутые тесты обновлены; релевантные проверки пройдены (см. этап 6).

### 5.4. Примеры запросов агенту

**Проверка плана без кода (Ask mode, перед Build):**

```text
[Ask mode]
[ОБЯЗАТЕЛЬНО: @файлы] @docs/plan-issue-<N>.md @docs/task-issue-<N>-dor.md
Проверь: (1) нет ли шагов вне Scope, (2) все ли критерии приёмки из DoR покрыты планом или тестами, (3) нет ли лишних файлов. Ответ: список замечаний или «план OK».
```

**Реализация после утверждения плана (Agent mode + обязательные документы):**

```text
[Agent mode]
Реализуй задачу строго по @docs/plan-issue-<N>.md и @docs/task-issue-<N>-dor.md.
Не выходи за Non-scope. Сохрани существующие data-testid, если в DoR указано.
После правок: запусти релевантные тесты и линт для затронутых файлов (команды из плана или из раздела 6.2 методички).
```

**Точечная доработка по согласованному фрагменту плана:**

```text
[Agent mode]
[ОБЯЗАТЕЛЬНО: @файлы] @docs/plan-issue-<N>.md — только раздел «As-built» / только шаг 3 по CSS.
Внеси изменения в перечисленные файлы; остальной код не трогай.
```

## Этап 6. Тестирование фичи

**Цель:** перед автоматическим/человеческим review убедиться, что фича работает **end-to-end**; тесты по scope — зелёные, остальные падения — **осознанны**.

### 6.1. Цикл при поломке

1. Описать, что сломалось.  
2. Приложить лог / скрин / шаги.  
3. Попросить агента найти причину.  
4. Внести правку.  
5. Перезапустить тесты / ручную проверку.

### 6.2. Команды по этому репозиторию

| Действие | Команда / место |
|----------|-----------------|
| Тесты только затронутого модуля | из `apps/frontend`: `yarn test app/components/<Component>.test.tsx` |
| Все тесты frontend | `cd apps/frontend && yarn test` (может падать на Apollo без провайдера — **не смешивать** с регрессией вашей фичи, если не трогали эти тесты) |
| Линт затронутых TS-файлов | `yarn eslint <paths>` в `apps/frontend` |
| Линт всего монорепо | с корня: `yarn lint` (может падать на **других** пакетах — зафиксировать в PR как pre-existing) |
| Сборка frontend | `cd apps/frontend && yarn build` |
| Ручная проверка UI | `yarn dev` → `http://localhost:3000` по пунктам из DoR **Acceptance criteria** |

**Ожидаемый результат:** фича работает; тесты по задаче зелёные; полный suite при необходимости **объяснён** в описании PR.

### 6.3. Примеры запросов агенту (отладка и повторный прогон)

**Цикл «упало — разберись — почини» (Agent mode):**

```text
[Agent mode]
Падает тест: вставь сюда полный вывод терминала (или последние 40 строк).
[ОПЦИОНАЛЬНО: @файлы] @apps/frontend/app/components/<Component>.test.tsx @apps/frontend/app/components/<Component>.tsx
Найди причину, предложи минимальный фикс, примени и снова запусти: yarn test app/components/<Component>.test.tsx из каталога apps/frontend.
```

**Проверка только релевантных тестов после мелкой правки:**

```text
[Agent mode]
Из apps/frontend выполни: yarn test <путь-к-файлу-теста>
Если упадут другие suite (Apollo и т.д.) — не чини их без запроса; напиши, pre-existing ли это относительно issue #<N>.
```

**Сверка ручных шагов из DoR без запуска браузера агентом:**

```text
[Ask mode]
[ОБЯЗАТЕЛЬНО: @файлы] @docs/task-issue-<N>-dor.md
По Acceptance criteria: какие пункты **только** ручные (браузер)? Составь чеклист из 5–7 галочек для меня перед PR.
```

## Этап 7. Автоматический (ИИ) code review на GitHub

**Цель:** до человека получить **краткий разбор diff**: что изменилось, риски, пробелы в тестах, краевые случаи.

### 7.1. Варианты инструментов

| Инструмент | Когда использовать |
|------------|-------------------|
| CodeRabbit, Copilot review, Bugbot | Если есть подписка / доступ к GitHub App. |
| **Агент Cursor** | Всегда доступен: открыть PR **Files changed** или `gh pr diff <N>`, вставить в чат с `@docs/task-issue-<N>-dor.md` и запросом структуры: Summary / Risks / Gaps / Edge cases / Verdict. |

### 7.2. Фильтрация замечаний

Агент часто предложит «улучшения» вне scope — **отсеивать** здравым смыслом; критичное по задаче — исправить и **push** в ветку PR.

### 7.3. Комментарий в PR

Имеет смысл вставить сжатый отчёт ИИ-review в обсуждение PR (как артефакт курса и для истории).

**Ожидаемый результат:** список осознанных действий до merge; опционально — дополнительный коммит по замечаниям.

### 7.4. Примеры запросов агенту (ИИ-review диффа)

**Обзор по открытому PR с MCP (актуальное состояние на GitHub):**

```text
[Agent mode]
[ОБЯЗАТЕЛЬНО: MCP] pull_request_read: method=get, method=get_files (perPage=100), method=get_check_runs для PR #<P> (PavelPleshkov/todo-fullstack).

[ОБЯЗАТЕЛЬНО: @файлы] @docs/task-issue-<N>-dor.md
Сопоставь изменённые файлы с scope задачи #<N>. Есть ли «лишние» файлы в PR? Краткий вердикт: merge как есть / сначала сузить PR / риски.
```

**Структурированный review без MCP (если вставили diff или ссылку на «Files changed» вручную):**

```text
[Ask mode]
Ниже diff PR (или опиши: я вставлю вывод gh pr diff <P>).
[ОБЯЗАТЕЛЬНО: @файлы] @docs/task-issue-<N>-dor.md

Ответ на **английском** (для комментария в GitHub), разделы:
1. Summary of what changed
2. Potential risks / regressions
3. Missing tests or validation gaps
4. Edge cases
5. Verdict (в границах issue #<N>)

Игнорируй pre-existing: полный yarn test с Apollo, lint вне затронутых файлов — только перечисли, если видишь в diff.
```

**Тот же review на русском (для внутреннего отчёта курсу):**

```text
[Ask mode]
[ОБЯЗАТЕЛЬНО: @файлы] @docs/task-issue-<N>-dor.md + тот же diff
Те же 5 разделов, ответ **на русском**, без копипаста в GitHub если не нужно.
```

## Этап 8. Ручной code review

**Цель:** человек подтверждает качество и поддерживаемость кода **как для обычного merge без ИИ**.

### 8.1. Что проверить

- Соответствие DoR и плану (включая **As-built**, если был).
- Лишние файлы в PR (частая ошибка: в PR попала **вся ветка**, а не только задача — см. раздел ниже).
- Имена, структура, тесты, безопасность, документация.

### 8.2. Комментарий в PR

Кратко зафиксировать: «Manual review completed, approved» + ссылка на критерии — для курса и команды.

**Ожидаемый результат:** код, который **понятен людям и следующим агентам**; можно **merge** в `main` (при зелёных/принятых проверках и отсутствии конфликтов).

### 8.3. Пример текста для комментария в PR (ручной review, курс §8)

Скопируйте в обсуждение PR и при необходимости дополните:

```markdown
## §8 Manual code review (human)

Выполнен ручной просмотр изменений в соответствии с курсом и ожиданиями к репозиторию.

**Проверено:** соответствие `docs/task-issue-<N>-dor.md` [и `docs/plan-issue-<N>.md` / As-built при наличии]; затронутые файлы; отсутствие лишнего scope; тесты по задаче; ручные шаги из DoR пройдены локально.

**Итог:** approve / готов к merge при [указать: CI / политика ветки].

*ИИ-review вынесен отдельным комментарием выше (если применимо).*
```

**Запрос к агенту подготовить такой комментарий по факту PR (Agent + MCP):**

```text
[Agent mode]
[ОБЯЗАТЕЛЬНО: MCP] Кратко: pull_request_read get для PR #<P>.
[ОБЯЗАТЕЛЬНО: @файлы] @docs/task-issue-<N>-dor.md
Сгенерируй готовый блок markdown для комментария в PR по шаблону §8 из @docs/Working-with-AI.md (раздел 8.3): подставь N, перечисли реально изменённые пути из PR, отметь pre-existing тесты если есть.
```

## Важно: узкий PR vs «вся ветка»

На примере **PR #10**: в один PR попали **18 файлов** — не только `Header.tsx` / issue #9, но и backend (Config, `tasks.service`), `README`, `CODEBASE_MAP`, `.cursor`, `yarn.lock` и т.д.

**Рекомендация для новых задач:**

1. Для **одной issue** — ответвляться от актуального `main`, делать **только** изменения по задаче, один PR.  
2. Если на ветке уже «лежит» много коммитов — либо **отдельные PR** по темам, либо явно описать в заголовке/теле PR **все** блоки работ и риски для ревьюера.

Иначе **Closes #9** в одном PR с несвязанным backend может путать историю и review.
